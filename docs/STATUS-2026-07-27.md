### P0-3 — why I did not fix it

**It is real.** `userHold(userId, assetId)` is one bucket for order reservations and withdrawal holds; `tradeFill` carries no `orderId`.

I did not fix it because the fix changes the ledger's **account model** — either a `purpose` dimension on `AccountRef` (schema + unique index migration) or separate account kinds. Eight services now build against that model. Doing it hastily while they land turns a real bug into a much worse one.

**It is also not a live bug, and that is precisely because P0-1 is true.** Nothing is deployed; no router is mounted. That sequencing is what buys room to do it properly.

Worth noting svc-trade already contains its own attributability: `orders.hold_amount` per order, with a test asserting `SUM(open orders.hold_amount)` equals the ledger hold balance per asset. The exposure is cross-module — a withdrawal settle consuming an order's reservation — not within trade.

**My proposal, for your view before I build it:** add `purpose` to `AccountRef` (`order:<id>`, `withdraw:<id>`, `null` for the rest), extend the accounts unique index, and make `tradeFill` / `orderHoldRelease` take the order id. One migration, one ledger-client change, updates to svc-trade and svc-ledger. Roughly a day, and it should land **before** anything is deployed rather than after.

### P0-2 — partly moot, but write it down anyway

svc-trade (#31) resolved it in practice: it treats its **own order store as source of truth** and derives `fillId` from `(marketId, engineSequence)` rather than reading users/assets/notional off the event.

So the drift risk you identified is closed. What is not closed is that the contract is **implicit**. Your ADR suggestion is the right call — one page saying "trade's order store is SoT, the event carries sequence and price only" — so nobody later assumes the event is self-describing.

### Three things worth your review specifically

**#37 `svc-protocol` — `custody-scan` finally ran against real code.** It has reported _"0 files across 0 Protocol Plane services"_ since I wrote it; it was an untested assertion. Now: 25 files, clean, first run, not weakened.

The design answer to _"what structurally stops us moving a user's funds"_: immutable EIP-1167 clone rather than an upgradeable proxy (_"an upgradeable account is a custodial account with extra steps"_), session keys that **cannot target the account itself** (closes every escalation path at once), 14 transfer selectors refused at grant time, and **no signing key in the service** — with a test that fails the build if one appears.

**Contract behaviour is never executed.** No Foundry/solc installed. Sockets recorded; nothing in `contracts/` should reach a chain holding value until the toolchain and audit sockets close. Two bugs were caught _by reading_ — a malleability constant 8 hex digits short, and an inverted validity window.

**#39 `svc-pay` — the conformance kit.** 128 tests any future adapter must pass. That is what turns "Stripe drops in with zero core changes" into something testable. It also surfaced the `pay:payout` MFA gap (fixed in #32) and mutation-tested its own new suites.

**#33 `svc-p2p` — escrow.** The sharpest bit: _"did the lock post?"_ is answered by **calling `escrowLock` again**, not by interrogating state — because escrow is pooled per (user, asset), so a refund against a lock that never happened would _succeed_, paying the seller out of another trade's escrow. There is a test that attempts exactly that raid.

## One operational hazard you should know about

svc-ledger's tests `TRUNCATE ledger.*` on the **shared** Postgres schema. Two worktrees running that suite at once will fail each other with what looks exactly like a real insufficient-funds bug.

Found by an agent that hit it, checked rather than re-ran, and proved its own service could not have caused it. `packages/db` already has `createTestDb` which allocates a unique schema per run — svc-ledger just is not using it. Worth fixing before either of us wastes an hour on a phantom.
